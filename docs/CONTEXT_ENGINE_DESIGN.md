# 모이다 회의 맥락 엔진 설계

작성일: 2026-10-07 · 2026-10-08 v0.4 보완

## 결론

현재 병목은 LLM 자체보다 LLM 앞단에 있다. 기존 질의 경로는 최근 발화와 질문에 같은 단어가 들어간 발화를 최대 9,000자까지 고르는 `recent+lexical` 방식이었다. 이 방식은 다음 관계를 표현하지 못한다.

- “그 일정”, “그건” 같은 대명사가 가리키는 앞 발화
- 처음 합의와 나중 정정·취소의 관계
- 결정, 이유, 제약, 담당자, 기한 사이의 관계
- 현재 회의와 프로젝트 자료·이전 회의 사이의 관계
- 후보 사실과 사람이 확인한 사실의 차이

해결 방향은 더 긴 단일 프롬프트가 아니라, 원문에서 출처를 잃지 않는 구조화 메모리를 만들고 질문이나 회의 변화에 맞춰 필요한 층만 조립하는 것이다.

## Notion에서 확인되는 구조적 차이

Notion의 공개 자료를 기준으로 보면 강점은 하나의 비밀 프롬프트가 아니다.

1. 문단, 업무, 데이터베이스 속성 등이 관계와 메타데이터를 가진 블록이다. 날짜 문자열도 담당자·상태·프로젝트와 연결된 속성으로 존재할 수 있다.
2. 긴 페이지를 span으로 나누고 임베딩하며, 저자와 권한 같은 메타데이터를 함께 저장한다. 기존 문서는 배치로, 편집은 실시간 경로로 갱신한다.
3. 워크스페이스와 연결 앱을 의미 검색하고, 요청 시점에 권한을 다시 필터링하며, 답변에 원문 출처를 붙인다.
4. 회의 요약은 전사뿐 아니라 회의 페이지에 적은 메모와 사전 문맥도 함께 사용한다.
5. Research Mode는 복잡한 질문에서 여러 검색을 수행하고 사용한 출처를 보여준다. 즉, 모든 답을 한 번의 즉시 추론으로 해결하지 않는다.

## 목표 동작

사용자는 계속 자유롭게 질문할 수 있다. 질문을 받으면 시스템이 내부적으로 다음 계획을 만든다.

```text
질문/회의 변화
  -> 의도와 대상 파악
  -> 필요한 맥락 층 선택
  -> 주제·사람·시간·상태로 후보 검색
  -> 정정/충돌/권한 검사
  -> 근거 예산에 맞춰 재정렬
  -> 답변 또는 필요한 경우에만 선제 제안
```

사용자가 직접 프롬프트를 설계할 필요는 없다. 내부 컨텍스트 플래너가 아래와 같은 계획을 만들되, 이 계획은 검색 범위를 정할 뿐 원문에 없는 사실을 만들 권한은 갖지 않는다.

```json
{
  "intent": ["SCHEDULE", "RATIONALE", "CHANGE"],
  "entities": ["출시 일정", "인증 심사"],
  "timeScope": "CURRENT_MEETING",
  "needs": ["latest_state", "superseded_state", "reason"],
  "sourceScope": ["transcript", "confirmed_outcomes", "linked_project_docs"]
}
```

## 맥락의 네 층

### 1. 원문 층

수정되지 않은 발화, 화자, 시각, 회의 버전을 보관한다. 모든 AI 결과는 이 층의 segment ID나 명시적으로 허용된 문서 구간을 인용해야 한다.

### 2. 에피소드 층

고정 글자 수가 아니라 주제 전환을 기준으로 인접 발화를 묶는다. 각 에피소드에는 주제, 참여자, 시간 범위, 한 줄 설명과 원문 segment ID 목록이 있다. “그건” 같은 표현은 이 경계 안에서만 연결한다.

### 3. 사실 상태 층

다음 타입을 후보로 추출한다.

- `DECISION`: 합의·확정된 선택
- `ACTION`: 담당자와 기한을 가질 수 있는 후속 작업
- `ISSUE`: 문제·위험·막힘
- `CONSTRAINT`: 예산, 정책, 일정 등 제약
- `QUESTION`: 아직 답이 없는 쟁점
- `CHANGE`: 기존 사실을 정정·취소·대체하는 변화

각 사실은 `candidate`, `confirmed`, `rejected`, `superseded` 상태와 confidence, source segment IDs, `valid_from`, `observed_at`을 가진다. 최신 문장을 무조건 진실로 덮어쓰지 않고 이전 버전과 대체 관계를 남긴다.

### 4. 업무 그래프 층

회의, 사람, 팀, 프로젝트, 문서, 결정, 할 일을 연결한다. 사용자가 확인한 연결만 장기 기억으로 승격하고, AI가 추측한 연결은 후보로 유지한다.

## 질의 시 컨텍스트 조립

초기 검색은 다음 후보를 합친다.

- 현재 주제와 최근 발화
- 질문과 의미가 가까운 에피소드
- 정확한 이름·날짜·티켓 번호를 찾는 어휘 검색
- 관련된 확인 완료 사실
- 해당 사실을 바꾼 이후 발화
- 사용 권한이 있는 연결 문서

후보를 합친 뒤 query-aware reranker가 질문과 중요도를 함께 보고 최종 근거를 고른다. 답변 모델에는 원문, 사실 상태, 충돌 정보, 출처 ID를 분리해 전달한다.

## 헤드 에이전트와 요약 API의 경계

요약 전용 API를 두는 것 자체는 합리적이다. 다만 사용자에게 보여줄 문서 요약과 헤드 에이전트가 서브 에이전트에 넘길 기계용 맥락 압축본은 수명과 품질 기준이 다르므로 같은 결과를 그대로 재사용하지 않는다.

- 사용자용 `/summary`: 사용자가 요청할 때 검토 가능한 요약·결정·할 일·미결 쟁점을 만들고 모든 항목에 원문 ID를 붙인다. 현재 화면의 저장 전 스냅샷도 처리하지만 자동 저장하지 않는다.
- 헤드 에이전트용 상태 압축기: 긴 회의에서 질문이 반복될 때만 버전별 `DECISION`, `CHANGE`, `ISSUE`, `ACTION` 상태를 구조화한다. 자유 문장 요약보다 출처 ID와 대체 관계가 우선이다.
- 서브 에이전트 입력: 상태 압축본은 검색 색인으로 사용하고, 최근 발화와 질문에 관련된 원문을 함께 전달한다. 최종 사실 문장은 반드시 원문을 다시 확인하고 인용한다.

모든 질문 전에 LLM 요약을 새로 만드는 방식은 사용하지 않는다. 현재 P0는 비용이 없는 결정적 `meetingBrief`, `meetingStateIndex`, 최근·관련 원문 선택을 사용한다. `meetingBrief`는 전체 회의의 반복 주제, 결정·변경·일정 신호, 최근 흐름과 원문 ID를 담고 8개 문장이 추가될 때 또는 사용자가 요청할 때 갱신할 수 있다. 사실을 대신하는 요약이 아니라 질문 전에 전체 방향을 잃지 않게 하는 탐색 지도다. 향후 저장형 압축기는 회의가 컨텍스트 예산을 넘고 후속 질문이 반복되거나, 명시적 요약 결과를 같은 회의 버전에서 재사용할 수 있을 때만 실행한다. 이렇게 해야 한 번의 압축 비용을 여러 질의에 나눌 수 있고, 침묵이나 짧은 맞장구 때문에 모델 호출이 늘지 않는다.

질문 입력은 `원본 질문 → 용어 후보 → 전체 회의 브리프 → 질문 관련 원문 → 허용된 팀 자료` 순서로 조립한다. 한두 글자 다른 회의 용어는 검색 범위를 넓히는 후보로만 사용하고 원본 질문을 덮어쓰지 않는다. 사용자는 `회의 근거만`과 `회의 + 일반 지식`을 요청별로 선택한다. 후자는 모델 내부의 일반 지식만 별도 영역에 허용하며 실시간 웹 검색으로 표시하지 않는다.

## 선제 제안 정책

‘AI가 알아서 말하기’는 계속 요약하는 기능이 아니라 이벤트 기반이어야 한다. 다음 조건 중 하나가 생겼을 때만 후보를 만든다.

- 결정 표현이 나왔지만 담당자나 기한이 비어 있음
- 같은 대상의 날짜·수치·상태가 바뀜
- 중요한 이슈가 일정 시간 동안 미해결 상태임
- 이전 확인 사실과 현재 발화가 충돌함
- 참조된 문서나 결정의 근거가 누락됨

노출 전에는 다음 게이트를 통과한다.

- 최소 근거 1개 이상
- 동일 제안 중복 해시 차단
- 주제별 cooldown
- 정정 가능성이 높은 발화는 대기
- 낮은 confidence는 자동 노출하지 않고 사용자가 질문할 때만 활용
- 모든 제안에 “왜 지금 표시했는지”와 원문 이동 링크 제공

## 단계별 구현

### P0 — 완료: 계층형 즉시 컨텍스트

- 질문 의도(`SCHEDULE`, `DECISION`, `ACTION`, `ISSUE`, `RATIONALE`, `CHANGE`, `STATUS`, `OVERVIEW`) 추론
- 집중/확장 답변 예산에 따라 직접 일치 발화의 앞뒤 한두 문장을 함께 선택
- 최근 발화, 주제 신호, 정정·변경 발화를 별도 역할로 표시
- 짧은 맞장구와 저정보 발화를 제외하고 제외 수를 사용량 정보에 표시
- 질문과 회의 맥락에서 기술·제품·리스크·실행·의사결정 검토 역할을 자동 선택
- 결정·변경·이슈·일정 원문 ID를 `meetingStateIndex`로 제공하되 사실 근거가 아닌 탐색 색인으로 제한
- 전체 회의의 주제·핵심 순간·최근 흐름을 원문 ID와 함께 담는 결정적 `meetingBrief` 제공. LLM 호출과 토큰 사용 없음
- `POST /api/meetings/{meeting}/ask/context`로 브리프만 갱신하며 질문 요청에서도 동일한 브리프를 재생성
- 질문의 원본을 보존하면서 회의 어휘와 편집거리 1~2인 단어를 최대 8개 검색 후보로 확장하고 화면에 공개
- 요청별 `MEETING_ONLY` / `MEETING_PLUS_GENERAL` 지식 범위와 서버 측 일반 지식 차단
- 원문 근거가 있는 결정·할 일·미결 이슈를 `retentionSuggestions` 초안으로 추천하되 자동 저장 금지
- 회의 제목·상태·버전을 포함한 context envelope 생성
- 답변 모델이 정정과 시간 순서를 비교하도록 지시
- 집중 4,800자/40문장, 확장 9,000자/80문장 상한과 원문 ID 검증 유지

이 단계는 의미 임베딩이 없는 안전한 개선이다. 단어가 완전히 다른 표현이나 여러 회의를 가로지르는 기억까지 해결하지는 않는다.

### P1 — 저장형 회의 메모리

- `meeting_episodes`
- `meeting_facts`
- `meeting_fact_sources`
- `meeting_context_runs`

전사 저장 후 비동기 추출하고, 재시도 가능한 상태와 추출 모델 버전을 기록한다. 사람이 검토한 기존 `meeting_outcomes`는 가장 신뢰도 높은 사실로 포함한다.

### P2 — 하이브리드 검색

- 문맥 설명을 붙인 에피소드 임베딩
- 한국어 형태소를 고려한 BM25 또는 동등한 어휘 검색
- Reciprocal Rank Fusion
- 질문 기반 reranking
- 권한과 삭제 상태를 질의 시점에 재검증

### P3 — 필요한 순간의 AI

- 변경·충돌·누락 이벤트 탐지
- 조용한 후보 큐
- confidence, 중복, cooldown 게이트
- 사용자가 승인한 제안만 결정·할 일로 승격

### P4 — 품질 평가

실제 회의에서 익명화한 질문 세트를 만들고 다음을 회귀 테스트한다.

- Context Recall@K: 필요한 근거가 선택됐는가
- Context Precision@K: 불필요한 발화가 얼마나 섞였는가
- Citation Precision: 답변 문장이 실제 인용으로 뒷받침되는가
- Temporal Accuracy: 최신 확정과 과거안을 구분하는가
- Contradiction Recall: 정정·취소를 놓치지 않는가
- Proactive Acceptance Rate: 선제 제안이 실제로 채택되는가
- Silence Quality: 필요 없는 순간에 조용했는가

## 제품 원칙

- 전사는 증거이고, AI 추출물은 후보이며, 사람의 확인은 사실이다.
- 프롬프트보다 데이터 관계와 출처를 먼저 설계한다.
- 긴 컨텍스트보다 정확한 컨텍스트를 우선한다.
- 자동화가 늘어날수록 삭제, 권한 회수, 감사 기록도 같은 수준으로 강화한다.
- 완전 자동 이해를 약속하지 않고, 불확실성과 빠진 범위를 사용자에게 보여준다.
